# Zenn 記事 PR 作成時の必須チェック

**push 後に必ず以下を全項目実行し、結果をユーザーに報告する。**
チェック未実施で「PR 作成完了」と報告しない。

## 1. 文章チェック（writing.md ルールに照合）

- 文体（です・ます調 / である調）がファイル内で統一されているか
- TL;DR が冒頭にあるか。ない場合は追加を提案する
- 見出し構成が「背景 → 本題 → 失敗談 / ハマりどころ → まとめ」の流れになっているか
- 「いかがでしたか？」「本記事では〜について解説します」等の AI 生成感のある定型文が無いか
- 一文が長すぎないか（目安60字）。「〜と思います」「〜かもしれません」が多用されていないか
- 太字記法 `**…**` の中に句点 `。` が入って見た目が崩れていないか
- 体言止めの連続でリズムが死んでいないか
- TL;DR や箇条書きの順序に論理破綻がないか（抽象→具体、または時系列で揃っているか）

## 2. コードブロック・図・リンクのチェック

- コードブロックに言語指定があるか（` ```python `、` ```sql ` 等）
- 図にキャプションと出典が付いているか
- 本文中の外部リンクをすべて死活確認する：
  ```bash
  for u in <URL...>; do
    code=$(curl -o /dev/null -s -w "%{http_code}" -L -A "Mozilla/5.0" --max-time 15 "$u")
    printf "%s %s\n" "$code" "$u"
  done
  ```
  403/404 が出たものは個別に判断（Medium 等は bot 検知で 403 を返すが正常）
- Zenn のリンクカード（行頭にURL単独）と、出典リンク（Markdown記法）の使い分けが意図通りか

## 3. 個人情報・機密情報の漏洩チェック

以下を本文中で grep / 目視確認する：

- 顧客・取引先の固有名詞、業種、規模、案件名
- 同僚・他社員の実名
- 社内システム名・テーブル名・スキーマ名・URLの内部ホスト
- 具体的な数値（売上・MRR・顧客数・SLA・件数など）→ 公開可否を確認
- 本番環境の構成・認証情報・トークンらしき文字列
- 第三者の発言を許可なく引用していないか

## 4. レピュテーションリスクチェック

- 顧客への責任転嫁になっていないか（「お客さんが要件を変えた」風の書き方は避ける）
- 過去/現在の所属企業・チーム・同僚への批判と取れる表現がないか
- 失敗の自己開示が、現職での重大インシデント告白になっていないか（前職の話として整理するか、抽象化する）
- 採用導線・宣伝が過剰になっていないか（HERP 等の公式リンクのみに留める）

## 5. Zenn フロントマター

- `title`: 検索される名詞を含むか（手段＋目的の形が望ましい）
- `emoji`: 1 文字のみ
- `type`: `tech` か `idea` のどちらが適切か
- `topics`: 5 つ以内に絞る
- `published`: PR で公開する場合は `true`、ドラフト保管なら `false`
- `publication_name`: IVRy publication に出す場合は `"ivry"`

## 6. PR 作成手順

- PR は **draft** で作成（`--draft`）
- ラベル `AI:100%` を付与
- PR 本文は短く：「なぜ / 何を」「変更点」「レビューしてほしい点」
- コミットメッセージに `Co-Authored-By` 行を含めない

```bash
gh pr create --draft --label "AI:100%" --title "<タイトル>" --body "$(cat <<'EOF'
## なぜ / 何を
- <意図>

## 変更点
- `path/to/file.md`: <変更内容>

## レビューしてほしい点
- <あれば>
EOF
)"
```

## 7. チェック結果の報告フォーマット

PR 作成後、以下の形でユーザーに報告する：

```
## 記事チェック結果
- 対象: <ファイルパス>
- PR: <URL>

### 1. 文章面
（writing.md ルールに照らした所見。問題なしならその旨を明記）

### 2. 個人情報・企業情報の漏洩
| 項目 | 内容 | 判定 |
（テーブルで列挙）

### 3. レピュテーションリスク
（観点ごとに低/中/高で判定）

### 4. リンク死活
（HTTP ステータス一覧）

### 結論
（公開して問題ないか、修正推奨点があるか）
```
